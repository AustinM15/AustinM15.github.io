The problem

Lack of visibility can be one of the most damaging vulnerabilities that your network can face. Specifically, not monitoring system and network logs is like giving threat actors a golden ticket to staying hidden inside your systems, without a real way to know they are there until they do real damage.

At my organization, I was left with the challenge of creating this visibility. No SIEM solution had been in practice yet, and so it was on me to decide which software, which configurations, and how to deploy this vital piece of security software that every system relies on today.

Constraints I started with

  • The tight budget constraints of a small business
  • Consumer-grade hardware lacking compute capabilities

The approach

I was starting from the ground, and so the only way was to go up. Now, I will take you through every generalized step I took to implementing a SIEM solution for my organization. All identifiable details will be redacted for security reasons, of course.

Choosing the Software

I chose an open-source, self hosted SIEM solution for my organization to satisfy my low budget constraints. Open source SIEM solutions are a great alternative to a SaaS SIEM such as Splunk or Microsoft Sentinel. The downside to my choice is this means I need to find a means of hosting the server.

Hosting the SIEM

Agent-based SIEM solutions work by having an agent installed on every endpoint you want to ingest logs from, that securely send this log data to a manager via secure protocols. This happens around the clock, so it is important for your SIEM manager to be hosted on a reliable server, maximizing uptime. Excessive downtime for a manager can mean missed logs and alerts if the agent’s buffers fill up. To avoid this buffer overflow and potential dropped logs, I chose to use an AWS EC2 instance to support the SIEM manager. I chose AWS for their high infrastructure reliability, granular access management (IAM), and cost effective scaling. This approach reduced the initial overhead cost of buying an on-site server.

Key Cloud Considerations for SIEM Deployment

While specific internal configurations are omitted for security reasons, several critical factors must be evaluated when deploying a cloud-based SIEM manager:

  • Static Addressing: Ensure that your manager server has a fixed IP address. When you configure agents, they will send logs and other telemetry to a specific target IP you configure at deployment. Any IP change in the manager will cut off communication from the agents, and could lead to agent buffer overflow and potential dropped logs.
  • Storage Isolation: Maintain separate storage volumes, one for your operating system and the other for log data. This way, if log volumes unexpectedly spike, a full volume won’t cause the operating system to crash, mitigating this risk.
  • Network Hardening: Ensure you have tight firewall rules. Make sure the only open ports are those necessary and required by the agents. Additionally, you should restrict access to these ports to the known IP ranges of your endpoints. Finally, restrict access protocols like SSH to trusted IPs used by those who need access to the server.
  • Identity & Access Control: Finally, avoid hardcoding access keys or API keys directly on the server. I would recommend instead that you attach a dedicated IAM role to the instance, and strictly enforce MFA for all accounts that can access the server console.

What I'd do differently

We spent the first six weeks on a query builder UI that almost nobody used — analysts wanted to write SQL. I should have shipped the streaming table alone and watched what people asked for next. The builder is still in the codebase, and I'd cut it.
